## 1. [xerj-org/xerj](https://github.com/xerj-org/xerj)
- **语言**：Rust
- **总 Star**：5,728
- **当日新增**：+715/天
- **简介**：本地 AI 检索引擎，一条命令把代码、文档、日志、PDF 全部建索引，让 coding agent 不再靠 grep 一行行翻文件、把整篇内容灌进上下文。对外是 Elasticsearch 兼容接口，现有客户端可直接复用；`xerj init` 会一次性把 MCP 与 skill 接进 Claude Code/Cursor，另有 `xerj search`（返回排序后的段落 + file:line）、`xerj def`（跳转定义）、`xerj gain`（统计它帮你省了多少）。主推场景是「参考式编程」：让 agent 先 clone 并索引实现最接近的开源仓库，检索别人怎么解决过这个问题，再动手写自己的代码——官方给出的对照实验是同等解题率（16/16）下输出 token 降到 1/2.7，日常使用反馈约 5 倍。二进制以 Apache-2.0 分发。
- **亮点**：它瞄准的痛点是真的：agent 的成本大头从来不是「答案写太长」，而是「为了找一段代码把整个仓库读进上下文」，用检索替代遍历确实是正确的成本曲线，而且「让便宜模型在有小抄的情况下赢过贵模型」这个定位比多数 RAG 项目诚实。但要用得清醒，先分清哪些数字能信：case study 只有 8 个任务、4 种语言，且是项目方自己的站点与方法，作为选型依据太薄；而它对比的 grep 基线（单次语料最高 1.06M 输入 token）也偏稻草人——现实里带 head 限制和路径过滤的 ripgrep 不会这么失控。真正的收益要靠 `xerj gain` 在自己的仓库上量出来，再决定要不要长期挂着。第二个必须自己读完的点是安全边界：README 明确说 `--insecure` 会关掉 TLS 与 API key 鉴权，此时任何能连到该端口的进程都是超级用户，能读能删所有索引，包括 `/_memory` 命名空间；默认只绑 127.0.0.1、换网卡明文绑定会拒绝启动，这套设计值得肯定，但也意味着不要把它开在共享开发机、CI runner 或任何可被同网段访问的机器上。还有个容易忽略的隐性成本：它的社区机制是「提交一份 field report PR 就算入会」，门槛很低所以参与量大，但在你给它索引专有代码之前，要确认这份回报里会不会带上路径、片段或索引摘要——这是拿隐私换 onboarding 的交易，不是纯捐赠。

## 2. [JuliusBrussee/caveman](https://github.com/JuliusBrussee/caveman)
- **语言**：Go
- **总 Star**：112,600
- **当日新增**：+433/天
- **简介**：一个「像原始人说话就省钱」的 coding agent 提速方案，4.0 版由六块组成，各自可单独开关：Say less 压缩回答文本（同一结论 63 token → 20 token，代码本身保持精确）；Read less 在模型读到之前先压缩日志、JSON、CSV 和测试输出（整会话输入 token 少 33.2%）；Auto 按每次提问挑选模型与推理强度（对比 Opus xhigh 便宜 54%、得分持平）；Blocks 让 agent 保留自己写过的脚本直接复用（一次测试运行 397 → 76 token）；再加 Waste fixes 定位浪费、Browse 压缩网页（129.8×）。规则设计上有两条硬约束：先给答案、句式参照航空维修手册用的受控英语 ASD-STE100，且冠词可以省但 not / never / only、数字与单位绝不删。`npx @caveman-ai/cli@latest` 一条命令接入，跑在本机、用你自己的 key 或订阅，支持 30 多个客户端；只有 Auto 需要注册（免费）。第三方数据：Adobe Research 引用它的论文测得单模型成本降至 1.4~2.4 倍，Elastic 在其 MCP 场景测得响应 token 少 63.6%，JetBrains 对 86 个真实编码任务做配对 A/B 得出「无可测质量损失」（p = 0.82）。
- **亮点**：这个项目最值得搬走的是它的两个「负面结论」。第一条：把用户的 prompt 改短会让答案变差，所以它绝不动你的输入——这直接否定了流行的「prompt 压缩」省钱路线，也解释了为什么它只做两端（agent 读到的工具输出、agent 说出的自然语言），因为 agent 会话里真正占大头的正是工具调用返回的日志与 JSON。第二条来自 JetBrains 的 A/B：会话主体是代码和工具调用，而「原始人语气」只作用于散文，所以收益有限（输出 token 仅少 8.5%）——这提醒我们别把演示里的 63→20 当成账单上的 63→20。要用的话有几个现实代价：它本质是在 agent 与模型之间插一层代理/改写器，这是新的信任边界，它持有你的凭据并可能改写流量，装到工作机前应当读一遍代码；回答被压成一句话结论后，事故复盘和新手带教时会丢掉你最需要的推理链，因此更合理的用法是按场景开关而不是全局默认开；它的 Auto「同分省 54%」来自作者自选的 85 道题，任何分数在你自己的评测集上都要重测一遍；另外整套语言规则建立在英语受控词表上，中文提问的输出行为与压缩比未必同样成立。

## 3. [anthropics/claude-plugins-official](https://github.com/anthropics/claude-plugins-official)
- **语言**：Python
- **总 Star**：39,174
- **当日新增**：+307/天
- **简介**：Anthropic 官方维护、也是官方背书的 Claude Code 插件目录：`/plugins` 是 Anthropic 自研自维的内部插件，`/external_plugins` 收录合作方与社区的第三方插件，后者需通过提交表单并经质量与安全审核。安装方式是 `/plugin install {插件名}@claude-plugins-official`，或在 `/plugin > Discover` 里浏览。插件目录结构固定：`.claude-plugin/plugin.json`（元数据，必填）、可选的 `.mcp.json`（MCP server 配置）、`commands/`、`agents/`、`skills/`、README。两条工程约定值得注意：marketplace 条目里的 `name` 是不可变 slug，一旦发布改名就会让已安装用户报 `plugin-not-found`，要改显示名请用 `displayName`，非要改名则在顶层 `.claude-plugin/marketplace.json` 的 `renames` 映射里写旧名→新名，加载器会在下次同步时自动迁移；若上游仓库只有 `SKILL.md` 而没有 plugin manifest，条目可用 `strict: false` 加显式 `skills` 数组直接声明，`source` 支持 git-subdir 形式的 url/path/ref/sha。
- **亮点**：作为「目录」它内容会变，但作为「规范」它已经足够值得抄：不可变 slug + `renames` 迁移表这套做法，正是任何内部 skill/插件市场迟早会踩的坑——用户装的是标识符而不是显示名，改名等于批量打断安装；以及用 `sha` 固定外部源，等于给插件装上 lockfile。更要紧的是 README 开头自己写的那句免责声明：Anthropic 不控制插件里的 MCP server、文件或其他软件，无法验证它们能正常工作，也无法保证它们不会变动——也就是说官方目录不等于可信供应链，插件市场本质是一个新的攻击面，而 `.mcp.json` 基本等同于一段「以你的文件系统和环境变量为作用域执行代码」的授权。落到实操，三条就够：装之前读它自己的仓库（尤其 MCP server 与 agent/command 定义），把 `sha` 或版本钉死，别让它静默更新；团队场景应在 devcontainer / 基线镜像里白名单化允许的市场 slug 与插件清单，并像审依赖一样把插件 diff 纳入代码评审；改名走 `renames`、显示名走 `displayName`，不要为了「更好听」动 slug。

## 4. [ruvnet/ruflo](https://github.com/ruvnet/ruflo)
- **语言**：TypeScript
- **总 Star**：75,155
- **当日新增**：+147/天
- **简介**：Claude Code 与 Codex 之上的「agent 元 harness」，前身是 Claude Flow，主张「Agent = Model + Harness」：模型负责写，harness 负责给它工具、记忆、循环、沙箱和控制器。Claude Code 里通过官方插件市场安装 `ruflo-core`（基础工具）、`ruflo-console`（可视化驾驶舱）、`ruflo-mods`（路由与策略执行，需 Claude Code 2.1.287+）；Codex 或其他 MCP 客户端则用 `npx ruflo@latest init wizard`，或把 `npx -y ruflo@latest mcp start` 作为 stdio MCP server 接入。它提供上百个专精 agent 与协同 swarm、跨会话的自学习记忆、向量检索，以及可让不同机器上的 agent 通信的 federation；控制台/TUI 追踪工作流、agent、模型、token 与成本，可以查看任意一次运行、检索并分诊失败、回放与对比。权限侧有明确的档位设计：Settings → Claude control 分 `read` / `write` / `manage` / `full`，每档再配 `ask` 或 `auto`，当前默认是最保守的 read + ask。MIT 许可。
- **亮点**：这类项目的根本矛盾在规模：上百个 agent、三百多个 MCP 工具、二十多条 CLI 命令，看起来是能力，实际是在每次调用时给模型增加「选错工具」的概率——工具面越大，误用与串味越难预测，README 自己也承认「你不需要学 314 个工具」恰恰说明这个数字曾是负担。所以不管是否采用，有三个设计该抄过来：把 token 与成本做成随手可看的驾驶舱，把每次运行做成可检索、可回放、可对比的日志，以及把权限做成显式阶梯（read/write/manage/full × ask/auto）并默认最保守那一档——这三样正是多数自建 agent 框架的缺失项。反过来，它宣传的两个亮点应当是最先被审视的：「自学习记忆」会把过去的错误模式持久化并影响后续会话，一旦某个被学进去的「有效套路」其实只是侥幸通过，你会得到复利式的偏差，而且这类隐式状态很难审计；「federation 跨机通信且不泄漏数据」需要一个具体威胁模型才可信——传输了什么、用谁的密钥加密、对端能读到哪些上下文，这些 README 层面回答不了。工程上还有一条：插件与 hooks 会自动改写路由行为，装到仓库前先 diff `init` 往 `.claude/` 写了什么，并把这类 harness 只在一次性分支上试点，别让它成为生产仓库默认的执行路径。

## 5. [lightseekorg/tokenspeed](https://github.com/lightseekorg/tokenspeed)
- **语言**：Python
- **总 Star**：2,512
- **当日新增**：+30/天
- **简介**：面向 agentic 负载的开源 LLM 推理引擎，目标定在「TensorRT-LLM 的性能 + vLLM 的易用性」。核心分三块：Scheduler 采用 C++ 控制面 + Python 执行面，把请求生命周期、KV cache 归属与 overlap 时序编码成有限状态机，并用类型系统在编译期强制 KV 资源的安全复用；Kernels 是一等公民的可插拔分层体系，有便携公共 API 与集中注册表，并包含 Blackwell 上针对 agentic 负载最快的 MLA（Multi-head Latent Attention）实现之一；Entrypoint 用 SMG 集成的 AsyncLLM 压低 CPU 侧请求处理开销。它已加入 PyTorch 生态，基金会点名的差异化正是「首个把控制面与执行面分离」与「把 kernel 当独立子系统」这两点；由非营利 LightSeek 基金会支持，NVIDIA 与 AMD 提供硬件与工程投入。已发布的实测包括 GB300 上单用户 685 tokens/s、Qwen3.8 2.4T 与 Kimi K3 的 Day-0 支持、MI355X 上的 Kimi K3 优化。MIT 许可。
- **亮点**：即便你永远不自建推理服务，它这个架构选择也值得读一遍：把调度和 KV cache 所有权从 Python 挪进带类型的 C++ 状态机，是把一类故障从「运行时偶发」提前到「编译期不通过」——推理栈最难查的问题往往不是崩溃，而是 KV 复用出错导致的静默错 token，不可复现、不可告警，只在用户抱怨「输出变奇怪」时才露头。用类型系统去守资源复用边界，比再加一层运行时断言更根本。可信信号排序上，「非营利中立 + PyTorch 生态收录 + NVIDIA/AMD 双家支持 + 对前沿开源权重做 Day-0 使能」要重于性能数字本身：后者几乎都是特定硬件（GB300/B200/MI355X）上的厂商自测，绝大多数团队既没有这些卡，也没有对应的 CUDA/ROCm 工具链维护带宽，拿来和自己的线上服务比等于比错分母。采用现实也要说清：换推理引擎是一项运维承诺，你同时接管了 kernel 兼容性、并行切分、显存与正确性回归，2.5k star 意味着生态磨合还在早期——真正自托管开源模型且规模可观的团队，合适路径是钉死版本、在自己的 prompt 集上做完质量回归再灰度，重点复核所有涉及 KV 前缀复用与新量化格式（FP4/MXFP4）的路径；至于只是调托管 API 或内部小模型服务的团队，读它的调度器设计收益更高，直接部署反而是负资产。
