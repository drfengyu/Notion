## 1. [NVIDIA/auto-ontology](https://github.com/NVIDIA/auto-ontology)
- **语言**：Python
- **总 Star**：5,173
- **当日新增**：+2050/天
- **简介**：NVIDIA 官方面向「让 agent 可靠地查数」放出的开源库，主张是 agentic analytics 的瓶颈在可靠性而非速度——「一个更快给出的营收指标，如果数字是错的就毫无价值」。做法是从企业元数据自动构建本体（ontology），把「数据在哪、含义是什么、该不该用、怎么用、从哪来、什么与它相似」这一层上下文沉淀下来，并通过 MCP、CLI、REST API 三种接口暴露给任意 agent harness，同时兼容客户已有的语义模型。能力按 Discover / Ground / Validate / Expose / Learn 五条组织：从元数据生成本体与 AI-ready 知识图谱、为指标与实体提供可信业务含义并调和跨系统的不一致定义、把生成的查询对照已认证定义与 lineage 校验且每个答案都返回 provenance、把经确认的修正与使用情况回灌本体。技术上是一个完整的全栈应用：前端 Next.js 16（React 19 + TypeScript + Tailwind CSS 4）配 Better Auth 与 Prisma（3000 端口），后端 FastAPI（Python 3.12+）+ LangChain 负责 chat 与 NL-to-SQL（3001），独立 ingestion worker 负责表格数据摄取与 embedding（3002），Postgres + pgvector 同时存应用元数据、目录/本体与向量库（5432），可选 HashiCorp Vault 存连接凭证，部署给 Helm chart 与 Docker Compose 两条路。数据源覆盖十个引擎：PostgreSQL、MySQL、Databricks、Snowflake、ClickHouse、Trino、Apache Kyuubi、HeavyDB、DuckDB、SQLite（后两者只走连接串）。推理默认走 NVIDIA NIM（`integrate.api.nvidia.com` 或自建 NIM），模型按 `REASONING` / `NON_REASONING` / `EMBED` / `RERANK` 四个角色各配「endpoint + api key + model」三元组并可逐级回落到 `DEFAULT_MODELS_*`，默认值为 `nvidia/nemotron-3.5-lightning-30b-a3b`、`nvidia/nemotron-3-embed-1b`、`nvidia/llama-nemotron-rerank-vl-1b-v2`；预测类问题在配置了 KumoRFM 时转给它。
- **亮点**：本期涨得最猛的一个（+2050 相当于其总 star 的 39.6%，典型「刚被大量知道」的曲线），也是最耐人寻味的一个：它以 Apache-2.0 开放源代码，README 里却用加粗块写明 **「This project is currently not accepting external contributions」**，并另附 `THIRD_PARTY_NOTICES.md` / `OPEN_SOURCE_NOTICE.license` 做合规声明——「开源但不收外部 PR」的官方姿态。另一处值得看的是它与标准的绑定：本体定义可导入导出为 **Apache Ossie**（语义模型交换开放标准，官方仓库里就有针对 NVIDIA 的 converter），走 `POST /api/model/import`、`/api/model/export` 或 Settings 页面，而不是自造私有格式——这对「客户已有 dbt / LookML 之类语义层」的团队是实际的接入点。此外它把「不确定就别答」做成了显式行为：数据不足以回答时报告会判定无法作答，Chat 里每个答案都展示 SQL、可下载 CSV 或转成图表。仓库 2026-04-27 建仓、409 个 fork、31 个 watcher，`releases.atom` 里唯一的条目是一个 9 月 1 日的 `pre-main-merge-backup` 备份 tag（releaseCount 为 0），也就是说近 2,000 的日增 star 与任何正式发版都无关，靠的是传播与官方背书；文档站在 nvidia.github.io/auto-ontology，text-to-SQL 评测另放在 `NVIDIA/ontology-sql-eval`（跑 BIRD 用）。

## 2. [JiaFeiMiao-K-Cat/DiscImageStudio](https://github.com/JiaFeiMiao-K-Cat/DiscImageStudio)
- **语言**：C#
- **总 Star**：6,650
- **当日新增**：+1778/天
- **简介**：一个中文优先的「光盘盘面可见图像生成与刻录」工具（Disc Image Studio），把任意图片转换成符合 CD / DVD / 单层 BD-R 物理层约束的数据，刻录后盘面上能肉眼看出图案，跨 Windows / Linux / macOS。桌面版主入口是三步流程：主页选介质类型建工程 → 设计页导入图片、用图层排版并在「影调」模块调抖动、伽马、亮度与灰阶档位 → 预览页核对盘面投影、导出页生成镜像或直接即时刻录。输出格式按介质分开：CD 导出带格式头的 WAV 音轨 + CUE（兼容 cdrecord、ImgBurn 等）或 RAW 音轨，DVD 导出 ISO，单层 BD-R 25 GB 支持纯绘图与 UDF 2.01 文件系统，三者都能把指定文件夹作为「随盘文件」放在内圈/外圈并在成品读回时用黄色标出文件区。灰阶走的是介质物理层的路子：CD 与 DVD 都用黑白二阶，CD 使用 `0D / AA`，DVD 扰码域使用 `A5 / 92`。另有一整套辅助标定流程（粗标定、边界标定、精细标定），从盘面照片估计内外半径与轨距分布，README 给了 Verbatim AZO DVD-R 标定前后的实拍对比——恒定轨距时径向十字线明显弯曲，改用三次轨距参数后接近直线。刻录既支持先出镜像再用外部软件刻，也支持「即时流式刻录」（边生成边刻、不保存完整镜像，BD-R 走 MMC 顺序写入，基于 Windows IMAPI2），但被明确标注为实验性功能且要求「不要使用非空白介质」。工程用 .NET 10（`global.json` 锁定 10.0.x），Windows 需要 Win10 2004/19041 及以上，发布包自带运行时；Linux / macOS 提供实验性 CLI（glibc linux-x64 / arm64、osx-x64 / arm64），有 `solve` / `encode` / `calibrate` / `simulate` / `selftest` / `cd-generate` / `cd-preview-warp` / `cd-preview-track` / `bd-generate` / `bd-info` 等子命令。源码按 `Cli` / `ImageIO` / `Core` / `Imaging` / `Burning` / `Cd` / `Dvd` / `BluRay` / `Iso` 分模块，DVD 引擎与架构各有一组自检与回归测试（`DvdImageSolver selftest`、`DiscImageStudio.ArchitectureTests`）。
- **亮点**：GitHub 上这个仓库**没有填 description**（`sidebarAbout.description` 为 null，榜单 `desc` 同样为空），所以本节简介全部取自 README 正文——而 README 本身有简中、繁中、英、日、土耳其、西班牙六种语言版本，说明作者是按「面向国际的中文项目」在维护。发布节奏是它今天上榜最直接的解释：`releases.atom` 显示 **v1.4.0 发布于 2026-11-04，也就是昨天**，此前 10-28 出 v1.3.3、11-02 一天连发 v1.3.4 与 v1.3.6，共 10 个 release，日增 1,778 几乎与最新版本发布同步，属于典型的「发版驱动上榜」。含金量体现在它没走调库的捷径：DVD/BD 侧自己处理 NRZI 通道电平编码、17PP/ECC、3T/6T 映射与 BD-R 几何，还写了 `PHYSICAL_MODEL_AUDIT.md` 这类物理模型审计文档，另有独立的小工具把原图处理成 0/255 黑白二阶 PNG。仓库 2026-08-23 建仓、238 个 fork、14 个 watcher，采用 GPL-3.0-or-later 并额外提供 `LICENSE-NOTICE.md` 做许可说明——对一个会分发自包含二进制的桌面工具来说，这条许可路径值得注意；同时它也是一个「物理介质黑客」类目里少见的完成度样本：标定、预览、读回模拟、CI 生成 EXE、MSIX 打包与签名流程都有文档（`docs/RELEASING.md`）。

## 3. [FareedKhan-dev/kimi-k3-in-c](https://github.com/FareedKhan-dev/kimi-k3-in-c)
- **语言**：C
- **总 Star**：10,336
- **当日新增**：+351/天
- **简介**：用可移植 C99 从零写出的一套 Kimi K3（2.78 万亿参数 MoE）CPU 推理引擎，声明无 BLAS、无框架、无 GPU，引擎本体只有 176 KB，峰值 RSS 实测 8.24 GB。它跑的是真实权重：checkpoint 共 96 个分片、1,560,936,091,448 字节（1.56 TB），其中路由专家 82,432 个（896 个 routed expert × 92 个 MoE 层），每个专家 17,547,264 字节 = 33,030,144 参数 × 0.53125 字节（MXFP4 的半个字节 + 每 32 字节共享一个 E8M0 scale）。之所以能在 8 GB 内存的机器上跑起来，靠 README 里说的「四次缩减」：其一权重本身就按 MXFP4 半字节存储；其二注意力用 KDA（线性注意力，state 大小不随序列增长，`k3_kda_step` 逐位跑朴素递推并与 PyTorch 参考实现对齐，因此从不物化大矩阵）；其三用 MLA 把 96 个头的 KV 压成一个 latent；其四把 93 层的 trunk 打包成可顺序流式的形态（每层一次连续区间读取并先校验连续性），于是「内存下限」变成一个可调节的旋钮，配合专家侧的 LRU 缓存。同一台机器上不同内存档位的实测是：8 GB 笔记本 26.5 秒/词元、32 GB 24.2 秒、64 GB 19.8 秒、128 GB+ 5.6 秒（模型全部驻留内存、不再有磁盘等待），README 强调这些机器的输出**逐字节相同**，只是时钟不同。工程细节还包括：从 1.56 TB checkpoint 的头部直接读取而不物化、拒绝猜测的 config reader、逐字节复刻的 tokenizer（与真实 Kimi K3 权重做 parity 校验）、AVX2 与 NEON kernel 精确复现标量归约顺序（`test_ops` 逐位校验）、与 PyTorch 参考实现做逐元素 logit 比对、可复现的 ids-in/ids-out 模式、cache trace 回放、以及在 MSYS2 MinGW 下移植 `O_DIRECT` / `pread` / `posix_memalign` / `getrusage` 后 `make test-all` 全绿。支持 Linux / macOS / Windows，需要约 1.7 TB 空闲存储（1.56 TB checkpoint + 109 GB 打包 trunk），另有官方 Kimi K3 XTML 聊天模式与 `ultra` 预设。
- **亮点**：标题里「2.78 万亿参数跑在 8 GB 内存」需要读完全文才能正确理解——**它不是把模型装进了内存，而是每一步都从磁盘流式读取整个模型**，代价是 8 GB 机器上 26.5 秒一个词元，直到 128 GB 内存档位才降到 5.6 秒；换句话说它证明的是「能跑」，而不是「能用」。这份诚实其实是它最值钱的部分：README 长 158 KB、分「Getting started」与「How it works」两部分，测量数据放在 `docs/data/`，架构与算法推导单独沉到 `docs/ARCHITECTURE.md`，甚至写明某些早期「关于算法的说法」当初只是断言而非代码约束、没有任何测试能捕捉其错误（因此被移进文档）。CONTRIBUTORS.md 逐条记录了 macOS / Windows / NEON 移植、聊天模式、`ultra` 预设、更快的 MXFP4 kernel 与一批 parser 修复分别是谁做的；README 中部还夹着一行「I am open to AI research roles and PhD positions」并附作者 CV 链接——这类个人求职信息夹在技术文档里，是判断项目动机的一个有用信号。仓库 2026-08-01 建仓，两天后出 v0.1.0，8-07 到 v1.0.0，10-02 到 v1.1.0 之后再无 release，共 3 个 release、1,631 个 fork；对一个依赖磁盘吞吐的 C 语言推理引擎而言，1,631 的 fork 数明显偏高，更像「跟着做实验」的读者比例。今日 +351 只占总 star 的 3.4%，是版本发布之后靠长尾传播维持的回榜。
